Code Explainer MCP

A Cloudflare Worker that explains source code with an ASCII architecture diagram, a functionality summary, and a component breakdown.

Overview Architecture API reference Languages Development Limitations

Overview

Code Explainer MCP is a single-file Cloudflare Worker. Given a code snippet and its language, it returns a Markdown report containing an ASCII architecture diagram, a summary of the code's core purpose, and a list of the main classes and functions with short descriptions.

All analysis runs inside the Worker using regular expressions and pattern matching. There are no LLM calls and no external runtime dependencies — the entire implementation lives in src/index.ts.

About the name. The project is named for the Model Context Protocol and retains workers-mcp in its deploy pipeline, but the current Worker does not use workers-mcp at runtime and does not speak the MCP JSON-RPC protocol. It serves a plain HTTP JSON endpoint (see API reference). See Known limitations for details.

Architecture

The Worker's default fetch export is the only entry point. It authenticates the request, then either runs an analysis (POST) or returns a static info page (GET/HEAD), answering any other method with 405. The analysis is orchestrated by explainCode, which calls four module-private helpers and assembles their output into Markdown.

Analysis pipeline

explainCode(code, language)
   │
   ├─▶ generateArchitectureDiagram   → ASCII diagram (classes, functions, imports, relationships)
   │       └─ extractBlock           → brace/indentation-matched declaration body
   │
   ├─▶ extractCoreFunctionality      → prose summary of primary/secondary purpose
   │
   ├─▶ extractComponents             → main classes + functions
   │       ├─ extractBlock
   │       └─ generateComponentDescription → per-component description
   │
   └─▶ assemble Markdown report

Helpers

Function Responsibility
explainCode Orchestrates the helpers and assembles the final Markdown report.
generateArchitectureDiagram Extracts classes (with inheritance), top-level functions, and imports using language-specific regexes, infers inherits/calls relationships, and renders an ASCII diagram.
extractCoreFunctionality Counts matches across purpose categories (network, UI, data processing, authentication, database, testing, algorithm, file system) and writes a prose summary of the primary and secondary purpose.
extractComponents Collects the main classes and functions (including JS/TS arrow functions) for the breakdown lists.
generateComponentDescription Returns a description for one component: an existing doc comment (JSDoc, Python docstring, or line comments) when present, otherwise a description inferred from code patterns.
extractBlock Returns a declaration's body: balanced { } brace matching for brace-delimited languages, or indentation analysis for Python.

Report format

A successful analysis returns Markdown with these sections:

# Code Analysis for <language> Code

## Architecture Diagram
```
<ASCII diagram>
```

## Core Functionality
<prose summary>

## Main Classes:
- <name>: <description>

## Main Functions:
- <name>: <description>

API reference

POST — explain code

Send a JSON body and the bearer token. params[0] is the source code; params[1] is the language.

POST /
Authorization: Bearer <SHARED_SECRET>
Content-Type: application/json

{
	"method": "explainCode",
	"params": ["function add(a, b) { return a + b; }", "javascript"]
}

Success returns 200 with Content-Type: application/json:

{
	"result": "# Code Analysis for javascript Code\n\n## Architecture Diagram\n..."
}

GET — info page

A GET request returns a small HTML page (200, text/html) describing how to call the endpoint.

Status codes

Status When Body
200 Valid POST, or a GET/HEAD { "result": "<markdown>" }, or the HTML info page
401 POST with a missing or incorrect Authorization header Unauthorized
503 SHARED_SECRET is unset or still the placeholder (the Worker fails closed) Service not configured: …
400 method is not explainCode, fewer than two params, or non-string params Invalid method or parameters
413 The code (params[0]) exceeds the maximum length (100,000 characters) Code exceeds the maximum length …
405 A request method other than POST, GET, or HEAD Method Not Allowed
500 Body is not valid JSON, or another error is thrown Error processing request

Example — curl

curl -X POST https://your-worker-url.workers.dev \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_SECRET_KEY_HERE" \
  -d '{"method":"explainCode","params":["function add(a, b) { return a + b; }","javascript"]}'

Language support

Class, function, and import detection use patterns selected by the language argument (case-insensitive). Languages outside this list fall back to generic patterns.

Language argument Detection notes
javascript, typescript, js, ts class … extends …, function name, ES import, and const x = (…) => arrow functions.
python class Name(Base):, def name, and from … import / import ….
java, c#, csharp class … extends … implements …, modifier-typed methods, and import …;.
any other value Generic patterns for classes, functions/def/braced declarations, and import-like keywords.

Each language also contributes extra keyword patterns to the core-functionality classifier (for example React/axios for JavaScript, Flask/Django for Python, JDBC for Java, Entity Framework for C#).

Development & deployment

Local development

Put a real secret in .dev.vars (gitignored) so wrangler dev injects it. The Worker fails closed: with the wrangler.jsonc placeholder YOUR_SECRET_KEY_HERE (or no secret), every POST returns 503. 

# .dev.vars
SHARED_SECRET=your-local-secret
npm install
npm run dev        # wrangler dev on http://localhost:8787

Quality checks

Task Command
Tests (Vitest, workers pool) npm test
Lint npm run lint / npm run lint:fix
Type-check (source) npx tsc --noEmit
Type-check (tests) npx tsc -p test/tsconfig.json --noEmit
Format npx prettier --write .
Regenerate binding types npm run cf-typegen

The root tsconfig.json excludes test/, so npx tsc --noEmit checks only the source; type-check the tests with their own config as shown above.

Deploy

wrangler secret put SHARED_SECRET   # set the production secret once
npm run deploy                      # workers-mcp docgen src/index.ts && wrangler deploy
Store the secret with wrangler secret put; never commit a real value into wrangler.jsonc. The placeholder there exists only so local wrangler dev has a value.

Known limitations

  • Heuristic, not parsed. Detection relies on regular expressions and substring checks rather than a real parser, so unusual formatting, nested generics, or uncommon syntax can be missed or misattributed.
  • Block extraction is heuristic. extractBlock matches balanced { } braces for brace-delimited languages and uses indentation for Python. Other indentation-based languages handled by the generic fallback still find no braces, so their component descriptions fall back to generic, pattern-derived text.
  • Substring call detection. Function-call relationships are inferred from name( appearing in another function's body, which can over-report calls when names collide with other identifiers.
  • Single-shot output. The report ends with a follow-up question, but the endpoint is stateless and cannot hold a conversation — each request is analyzed independently.
  • Auth comparison. The bearer token is checked by comparing SHA-256 digests in constant time, leaking neither the secret's content nor its length through response timing. The Worker also fails closed, returning 503 until a real SHARED_SECRET is configured. Add rate limiting in front of the Worker for higher-assurance deployments.
  • Input size cap. Code longer than 100,000 characters is rejected with 413 before analysis, bounding worst-case regex work on adversarial input.
  • workers-mcp is vestigial. It remains a dependency and docgen runs at deploy time, but the Worker does not define a WorkerEntrypoint class or use the MCP protocol at runtime. The served behavior is entirely the hand-written fetch handler.
